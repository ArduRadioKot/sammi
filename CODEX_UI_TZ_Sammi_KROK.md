**Статус:** готовое техническое задание для coding agent. **Scope:** преимущественно frontend (React/Vite/TypeScript) + типизированный service adapter, демо-данные и тесты UI. Не менять бизнес-ядро Sammi без необходимости. **Язык пользовательского интерфейса:** русский.

> **Инструкция агенту:** Ты находишься в корне репозитория `ArduRadioKot/sammi`. Не ограничивайся планом или макетами: **реализуй работающий frontend-модуль** по этому ТЗ. Сначала прочитай локальные `README.md`, `PROJECT_MAP.md`, `SKILL-feelistic-aries.md`, `package.json`, текущий routing, App shell, страницы `Companies`, `People`, `Tables`, общую дизайн-систему и слой `src/services/`. Найди реальные файлы самостоятельно: не исходи из предположения, что имена компонентов совпадают с названиями ниже. Отчёт о выполнении должен включать список изменённых файлов, готовых функций, того, что не подключено к backend, и результаты тестов.

## 0. Цель и непреложные требования

**Что строим:** экран «Карта ЛПР» — рабочий инструмент для менеджера, который видит сотрудников корпоративного клиента, **структуру принятия решений**, отношения, влияние, историю взаимодействий, пробелы в покрытии, может менять данные и фильтровать граф. Нужна убедительная демонстрация обмена с mock CRM. Это **не** диаграмма оргструктуры и **не** географическая карта адресов.

**Обязательные функции кейса КРОК — все 7:** (1) выбор клиента; (2) карта людей; (3) связи; (4) оценка отношений; (5) история взаимодействий; (6) редактирование; (7) фильтрация. На защите объяснить: какие сведения приходят из CRM, какие появились в карте, что возвращается в CRM. AI, аналитика, автообновление и коллаборация — только после этих функций.

### Технические инварианты Sammi (по README/PROJECT_MAP; перед изменениями перепроверь локально)

- React 19 + TypeScript + Vite + React Router; Next.js runtime уже удалён — **не возвращать Next.js, Server Components, next/link**.
- Основные app routes: `/app`, `/app/tables`, `/app/tables/:id`, `/app/companies`, `/app/people` и др.; новый вложенный route должен быть совместим с текущей маршрутизацией.
- `src/styles/tokens.css`, `src/lib/motion/tokens.ts`, `SKILL-feelistic-aries.md` — дизайн-источник; стиль Sammi: warm ivory для приложения, emerald/teal signal, restrained borders, Instrument Sans, IBM Plex Mono для метрик.
- В `src/services/` есть разделение UI/transport. Нельзя делать `fetch()` прямо из 20 компонентов; использовать существующий pattern API client/store/hooks.
- Backend `apps/api/` (FastAPI/PostgreSQL); прежний API таблиц и CSV менять/ломать нельзя.
- `/api/v1/tables/{id}/map` — **географическая карта**, НЕ используем её как API карты ЛПР.
- `VITE_ENABLE_DEMO_DATA` существует, но demo route таблиц не входит в нормальный flow; не подключай глобально фикстуры к продовым данным.
- Документированные ограничения: CRM пока нет; логин beta; client-side фильтры Table Editor ограничены загруженной страницей.

**Сначала проведи аудит фактической структуры проекта**, затем реализуй изменения. Не выдумывай несуществующие функции и не заменяй пользовательские данные тестовыми автоматически.

**Кнопки и контекстные действия:** `Открыть карточку`, `Добавить связь`, `Зафиксировать встречу`, `Изменить оценку`, `Показать путь` (P1). Каждое действие доступно из очевидного UI, проходит валидацию и отражает реальный статус сохранения.

### 4.3. Визуальная семантика графа

**Узел контакта:**
- Имя (с усечением и tooltip/full text), должность/сокращённый отдел; компактный круглый avatar с инициалами при отсутствии фото; без использования вымышленных портретов реальных людей.
- Первый приоритет визуального кодирования: **роль в решении** (ЛПР, влияющий, эксперт, пользователь, закупки, роль неизвестна) — иконка/label/border, не только цвет.
- Второй приоритет: **отношение к предложению** (поддерживает, нейтрален, скептичен, неизвестно) — небольшой маркированный indicator, доступный текстом. Не делать красный цвет синонимом «враг».
- Третий: активность коммуникаций (последний контакт, stale state), через лёгкий badge/tooltip, не кислотное свечение.

**Рёбра:**
- `reports_to`: управленческое подчинение, направленная сплошная линия.
- `influences`: влияние на решение, пунктир/стрелка и отдельная легенда.
- `collaborates_with`: рабочее взаимодействие, тонкая линия без стрелки.
- `introduced_by`: подтверждённая цепочка знакомства, отдельный тип.
- `unknown/unverified`: необязательная пунктирная светлая линия и подпись «Не подтверждено».
- **Не отображать** все рёбра одновременно при высокой плотности: filters, grouping, declutter, фокус на 1-hop/2-hop соседей.

Сила связи 1–5 и уверенность `verified | inferred | unknown` **разные поля**. Цветами можно показывать выбранный смысл, но hover/details обязаны раскрывать type и source. Взаимодействие «менеджер Sammi ↔ клиент» концептуально не то же ребро, что «сотрудник клиента ↔ сотрудник клиента».

### 4.4. Drawer карточки контакта

При выборе узла справа открывается drawer шириной ~360–420 px (адаптировать под токены/viewport), заголовок: имя, должность, отдел, статус сведений и дата обновления.

**Tabs:**
1. `Обзор`: ключевые поля, роль в инициативе, оценка отношения, важность/влияние, доступность/владельцы коммуникации, источник.
2. `Связи`: входящие/исходящие, тип связи, сила, подтверждение и действие редактирования.
3. `История`: timeline взаимодействий (дата, тип, автор, summary), фильтр по типу, `Добавить взаимодействие`.
4. `Источники`: источник каждого спорного свойства, когда синхронизировано, пометка оценочного суждения. Для демо допускается упрощённая вкладка.

**CRUD flows:**
- Contact edit: `Редактировать` → форма → validate → `Сохранение…` → success/error → закрыть по явному действию.
- Relationship add: выбрать контакт-источник + контакт-цель (не один и тот же), тип, направление, сила, комментарий, источник/дата → сохранить → новая линия.
- Assessment edit: отдельные селекты `Роль в решении`, `Влияние 1–5`, `Позиция: поддерживает/нейтрально/скептически/неизвестно`, дата, evidence/комментарий. Не присваивать stance автоматически по title.
- Interaction add: date/time, type (meeting/call/email/event/note), participants, summary, author (из auth), visibility. Системные timestamp только из результата persistence layer.
- Delete — только если backend поддерживает и есть подтверждение; скрывать управление у viewer.

**Empty values:** `Неизвестно` / `Нет подтверждённых данных`, никогда не выводить 0 или «Нейтрален» как fallback для отсутствующих сведений.

### 4.5. Список контактов как альтернативное представление

Колонки: имя, должность, отдел, роль в решении, сила влияния, отношение, последний контакт, источник/свежесть. Синхронизация selection/filter с графом; clicking row открывает тот же drawer. При недостатке данных показывать unknown. Search/filter применяются **ко всем контактам выбранной компании**: либо серверный filter, либо фронт загружает полный ограниченный демо-набор целиком — явно документировать ограничение.

### 4.6. «Покрытие и риски» (P1, только после P0)

Виджеты: покрытие критических ролей; подразделения без подтверждённого контакта; люди, с которыми давно не общались; риски зависимости от единственного контакта; недостаточно достоверные связи. Каждый показатель → кликабельный список фактов/контактов; рядом методика и период. **Без декоративных процентов при отсутствии знаменателя**.

### 4.7. «CRM-обмен» — обязательная объясняемость интеграции

Нужен компактный экран/panel `Источник данных`:
- `Получено из mock CRM`: компания, контакт, должность, подразделение, история событий (если есть).
- `Дополнено в карте`: роль в решении, влияние, отношение, сеть связей, комментарии.
- `Планируется передать обратно`: изменённые поля/события, статус `pending / synced / failed`.
- Если реальный backend не подключён: ярлык `Демонстрационный режим`, описание границы API; **не писать «Синхронизировано с CRM КРОК»**.
- Кнопка `Предпросмотр обмена` может формировать настоящий diff локальных данных и базового mock snapshot; `Применить` показывать только при реально реализованной записи в локальное mock-хранилище или API. Текст должен раскрывать, куда именно сохранены изменения.

## 5. Полный перечень состояний UI

Создать единый контракт состояния данных, а не хаотические `isLoading` внутри карточек.

| Состояние | Поведение |
|---|---|
| `initial/loading` | Skeleton shell + canvas placeholders, без скачков размеров |
| `empty_account` | «Компания не найдена» / «Нет доступа» и выход к компаниям |
| `empty_graph` | Нет контактов: CTA «Добавить контакт» (если можно) / объяснение демо |
| `no_filter_matches` | «По условиям ничего не найдено» + `Сбросить фильтры` |
| `node_selected` | Подсветка узла, hover соседей, detail drawer, URL/query state опционально |
| `editing` | Чётко видны editable поля и dirty state; при закрытии — защита от потери формы |
| `saving` | Disabled повторная отправка, spinner/progress только на действии |
| `saved` | Результат API/adapter подтверждён, UI пересчитан |
| `save_error` | Ошибка с retry, несохранённые значения не объявляются сохранёнными |
| `permission_readonly` | Viewer видит данные, edit controls disabled/hidden с понятным объяснением |
| `offline/network_error` | Повторить и не терять несохранённые изменения |
| `stale_source` | Дата и предупреждение, если запись устарела |
| `unknown` | Явно «Нет данных», без fabricated metric |

Обрабатывать `ESC`/outside-click для drawer без потери несохранённой формы; `Enter` в search, фокус и screen-reader labels.

## 6. Адаптивность и доступность

- **Desktop ≥1280 px:** canvas + expandable left filters + right drawer, максимальная концентрация на карте.
- **Tablet 768–1279:** боковая панель фильтров collapsible, drawer overlay, canvas адаптивен, нельзя перекрывать toolbar.
- **Mobile 320–767:** по умолчанию список контактов, кнопка переключения к карте доступна; карточка full-screen sheet; фильтры в drawer; toolbar не обрезается по горизонтали. Минимум 44×44 px для touch targets.
- Keyboard: Tab/Shift+Tab, Enter открыть карточку, Esc закрыть, стрелки по списку; граф должен иметь **доступную альтернативу** в виде списка.
- WCAG-подобные основы: читаемые подписи, контраст, видимый focus; цвет не единственный носитель смысла; aria-label для иконок; `prefers-reduced-motion`.
- Проверка в light/dark Sammi и без реальных фотографий.

## 7. Дизайн-спецификация: продолжение Sammi, не новый бренд

**Обязательное:** перед редизайном прочитать `SKILL-feelistic-aries.md` и текущие токены. Не создавать отдельную дизайн-систему с произвольным фиолетово-синим градиентом, карточками «как в типичном AI SaaS» или стеклянными оверлеями по всей странице.

- **Base surface (app):** warm ivory + светлые нейтральные контуры; тёмная тема — emerald/near-black согласно tokens.
- **Accent:** teal только для selection, actions и active navigation. Статусы используют доступные семантические цвета + текст.
- **Typography:** Instrument Sans интерфейс; Instrument Serif не применять к dense CRM data; IBM Plex Mono только timestamps, IDs, компактные метрики.
- **Density:** много информации, но чёткая иерархия; граф наибольший, ширина drawers и chips контролируемая; минимум декоративных рамок.
- **Motion:** 120–220 мс для drawer/selection (ориентир, если не противоречит текущим motion tokens), без постоянного движения узлов после стабилизации layout. Редуцированная анимация соблюдается.
- **Radius:** для плотного технического UI небольшие/средние по текущим токенам, не округлять всё на 24px.
- **Graph layout:** группа по отделам или роли; стабильно между перезагрузками при том же наборе, сохранённые позиции необязательны для MVP. Если выбираешь force layout — seed/stop stabilization и fit view после первой укладки.
- **Контент:** живые реальные русский labels: «Принимает решение», «Влияет на выбор», «Последняя встреча», «Сведения не подтверждены», «Показать связанные контакты». Не placeholder «Lorem ipsum».

## 8. Frontend domain types и контракты адаптера

Создай **типизированные** структуры и слой трансформации данных, пригодные для подключения к backend. Пример интерфейсов (подгони под соглашения проекта):

```ts
type RelationshipType =
  | 'reports_to'
  | 'influences'
  | 'collaborates_with'
  | 'introduced_by';

type StakeholderRole =
  | 'decision_maker'
  | 'influencer'
  | 'initiator'
  | 'user'
  | 'technical_expert'
  | 'procurement'
  | 'unknown';

type Position = 'supportive' | 'neutral' | 'skeptical' | 'unknown';
type Confidence = 'verified' | 'inferred' | 'unknown';

interface AccountSummary {
  id: string;
  name: string;
  industry?: string | null;
  updatedAt?: string | null;
}
interface StakeholderContact {
  id: string;
  accountId: string;
  name: string;
  title?: string | null;
  department?: string | null;
  role: StakeholderRole;
  influence?: 1 | 2 | 3 | 4 | 5 | null;
  stance: Position;
  lastInteractionAt?: string | null;
  source?: string | null;
  verifiedAt?: string | null;
}
interface StakeholderEdge {
  id: string;
  accountId: string;
  fromId: string;
  toId: string;
  type: RelationshipType;
  strength?: 1 | 2 | 3 | 4 | 5 | null;
  confidence: Confidence;
  evidence?: string | null;
  updatedAt?: string | null;
}
interface Interaction {
  id: string;
  accountId: string;
  contactIds: string[];
  type: 'meeting' | 'call' | 'email' | 'event' | 'note';
  occurredAt: string;
  summary: string;
  authorName?: string | null;
  source?: string | null;
}
interface StakeholderSnapshot {
  account: AccountSummary;
  contacts: StakeholderContact[];
  edges: StakeholderEdge[];
  interactions: Interaction[];
  dataSource: 'demo' | 'mock_crm' | 'api';
  fetchedAt: string;
}
```

**Адаптер (пример обязанностей, не реальные endpoints):**

```ts
interface StakeholderRepository {
  listAccounts(): Promise<AccountSummary[]>;
  getSnapshot(accountId: string): Promise<StakeholderSnapshot>;
  updateContact(accountId: string, id: string, patch: Partial<StakeholderContact>): Promise<StakeholderContact>;
  createEdge(accountId: string, input: Omit<StakeholderEdge, 'id'>): Promise<StakeholderEdge>;
  updateEdge(accountId: string, id: string, patch: Partial<StakeholderEdge>): Promise<StakeholderEdge>;
  addInteraction(accountId: string, input: Omit<Interaction, 'id'>): Promise<Interaction>;
  getSyncPreview?(accountId: string): Promise<unknown>;
}
```

**Ключевые правила:**
- Если API ещё не существует, можно сделать полноценный **локальный DemoRepository** с сохранением изменений в отдельно namespaced localStorage/IndexedDB только для демо, плюс краткое сообщение об ограничениях; при необходимости сбрасывать demo seed отдельной кнопкой. **Нельзя утверждать, что данные ушли в PostgreSQL/CRM, если это не так.**
- Если доступен новый реальный API — подключай через существующий auth-aware API client в `src/services/`. Не оборачивать 404 в фикстуру молча.
- `VITE_ENABLE_DEMO_DATA=false`: не подменять пустую компанию демо-компанией. Демонстрационный режим должен включаться явно и содержать заметный source label.
- Не брать CRM для списка компаний из случайной пользовательской spreadsheet без стабильной связи `accountId`; если нужно, опиши migration/adapter constraint и реализуй простой demo catalog.
- Страницы и UI-компоненты ничего не знают о transport (`fetch`, axios, JSONB schema).
- Add/Edit operations валидируют accountId, target, source; серверные ошибки корректно показываются.
- Не использовать географический `/tables/{id}/map` в этом модуле.

## 9. Демо-данные и сюжет конкурса

Сделай специально **вымышленные** сценарные данные, отделённые от пользовательских:
- 3 условных корпоративных клиента, у каждого 15–30 сотрудников, 3–6 подразделений; имена и компании вымышленные и не указывают на КРОК/реальных клиентов.
- У первого клиента: ИТ/ИБ/финансы/закупки/бизнес, один ЛПР без подтверждённого прямого контакта, несколько влияющих, один скептически настроенный, один давно не контактировавший участник, 20+ типизированных связей и история 10+ событий.
- Второй клиент заметно другой, чтобы показать R1 и корректную изоляцию.
- В демо нужно уметь **реально** открыть карточку, отредактировать assessment, создать связь, добавить взаимодействие, сохранить и перезагрузить состояние. Отдельная кнопка «Сбросить демо» в меню демо.
- Отсутствующая информация маркируется `unknown`, не «нейтрален» по умолчанию.

**Сквозной сценарий:** открой «Северный банк (демо)» → найди ИБ → увиди отсутствие активной связи → создай через редактор связь/зафиксируй встречу → измени stance и посмотри изменённую визуализацию → покажи список исходящих mock CRM изменений.

## 12. Вне текущего scope / зависимости от backend

**UI-итерация не может автоматически выполнить server-side задачи.** Если отсутствуют endpoints и модели для контактов/связей/interaction history, необходимо:
- реализовать UI + service interface + локально сохраняемое демонстрационное хранилище;
- добавить `BACKEND_CONTRACT_STAKEHOLDERS.md` с точными payload/permissions/errors/migrations как контракт для отдельного backend-спринта;
- не переписывать `apps/api/` без прямого поручения и не симулировать серверную запись.

Новые (предлагаемые, **не подтверждённые как существующие**) endpoints, которые backend-разработчик может реализовать позже: `GET /api/v1/accounts`, `GET /api/v1/accounts/{id}/stakeholders`, CRUD `/contacts`, `/relationships`, `/interactions`, `GET/POST /crm-sync/...`.

## 13. Что намеренно НЕ входит в UI-спринт

- ML/LLM-рекомендации, генерация объяснений и GigaChat/Yandex интеграция, если нет реального API.
- Настоящая синхронизация с CRM КРОК — доступ к ней не предоставляется по кейсу.
- Биллинг, waterfall enrichment, многоступенчатые paid provider integrations.
- Экспорт всей истории в сторонние сервисы, рассылки сотрудникам клиента, сбор данных из социальных сетей.
- Переработка маркетингового сайта и дизайна всего Sammi.
